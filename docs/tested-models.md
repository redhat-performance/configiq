# Tested-model pipeline

ConfigIQ's tested-model system turns measured inference results into
configuration-specific performance-envelope classifiers. The pipeline and its
source code live in this repository; `configiq-tested-models` is no longer the
production pipeline.

## Runtime contract

The pipeline produces one sanitized bundle containing:

```text
registry.json                 Webapp-facing pair and classifier metadata
dashboard/<pair-id>.json     Sanitized dashboard data
triton/<pair-id>/             Triton FIL model repositories
  config.pbtxt
  1/xgboost.json
```

The ConfigIQ container reads `registry.json` from `TESTED_MODELS_DIR`, which is
`/tested-models` by default. The deployment repository mounts the host bundle
at that path and mounts its `triton/` subdirectory at `/models` for Triton.
The webapp endpoint is `GET /api/tested-models`; dashboard data is served from
`GET /api/tested-models/dashboard/<pair-id>`.

The deployment-owned `k2_horizon` vLLM model is separate from the generated
FIL bundle. It shares the Triton server but is not generated by these scripts.
The deployment-owned `qwen3_8b` model is a fallback and is normally unloaded.

## Data boundary

Ground-truth extraction runs only from an approved environment. The legacy API
extractor receives its source endpoint through `PERF_DATA_API_URL`; the GitHub
publisher reads the approved S3 aggregate with an OIDC read-only role. Neither
source location is written to published artifacts. Extraction removes run IDs,
UUIDs, MLflow identifiers, timestamps, raw runtime arguments, and other
administrative fields before publication. The S3 importer includes only models
in `public/config.json`'s `testedModels` list and retains all source version
labels. Consumers can select versions for a particular comparison later.

The scheduled GitHub Actions workflow consumes a pinned revision of the public
`redhat-performance/configiq-performance-data` Hugging Face dataset. It uploads
only the sanitized registry/Triton/dashboard bundle as a workflow artifact.
Raw parquet files, source identifiers, and training work files are not
published by that workflow.

## Production workflow

### 1. Publish ground truth

The GitHub workflow `.github/workflows/publish-performance-data.yml` downloads
the aggregate, prepares sanitized Parquet pairs, and compares their content
with the public Hugging Face dataset. Pushes to
`feat/ground-truth-vs-aisim` run this preparation and comparison without
publishing. The workflow also runs at 00:00 Monday in `America/New_York` on
the default branch. Scheduled publishing requires the GitHub repository
variable `PERFORMANCE_DATA_PUBLISH_ENABLED=true`; otherwise scheduled runs
only prepare and compare. A manual run on `main` publishes only when its
`publish` input is selected. Unchanged content is never uploaded.

Hugging Face publishing uses a Trusted Publisher on the dataset repository,
restricted to `redhat-performance/configiq`, branch `main`, and workflow
`publish-performance-data.yml`. No persistent Hugging Face token is stored in
GitHub. The AWS read-only role must trust the repository's OIDC subject for
`main` as well as any branch used for S3 dry runs.

The earlier API extraction path remains available from an approved data
environment:

From the approved data environment, extract and publish a sanitized dataset:

```bash
uv sync --group tested-models
export PERF_DATA_API_URL="https://<approved-data-source>"
uv run --group tested-models python scripts/tested_models/discover_data.py --accelerator H200
uv run --group tested-models python scripts/tested_models/extract_datasets.py
uv run --group tested-models python scripts/tested_models/publish_ground_truth.py
```

Set the resulting Hugging Face revision as the GitHub repository variable
`TESTED_DATASET_REVISION`. Do not commit the dataset or its source credentials.

### 2. Build and validate the bundle

The repeatable build is `.github/workflows/tested-models.yml`. It runs the
regression tests, downloads the pinned dataset, creates grouped leakage-safe
splits, fits labels from training rows, trains XGBoost classifiers, exports
Triton FIL repositories, builds dashboard payloads, and validates the registry.

Run the same sequence locally when debugging:

```bash
uv run --group tested-models pytest scripts/tested_models/tests -q
uv run --group tested-models python scripts/tested_models/download_ground_truth.py --revision "$TESTED_DATASET_REVISION"
uv run --group tested-models python scripts/tested_models/split_dataset.py
uv run --group tested-models python scripts/tested_models/label_data.py
uv run --group tested-models python scripts/tested_models/train_classifiers.py
uv run --group tested-models python scripts/tested_models/export_triton.py
uv run --group tested-models python scripts/tested_models/build_dashboard.py
uv run --group tested-models python scripts/tested_models/build_registry.py
uv run --group tested-models python scripts/tested_models/validate_artifacts.py
```

The generated bundle is under
`data/tested-models/stage6/registry/`. It is a build artifact and is ignored
by Git.

### 3. Install on hosts

Use the matching `configiq-deploy` checkout and its
`deploy-tested-models.sh` installer. The installer stages and atomically
replaces the host bundle at `/var/lib/configiq/tested-models`; it does not
rebuild the application image. After installation, it explicitly loads the
generated FIL models into Triton. A webapp restart is not required.

For a remote host:

```bash
./deploy-tested-models.sh \
  --host <host> \
  --ssh-key ~/.ssh/configiq-instance \
  --bundle data/tested-models/stage6/registry
```

Run the installer for each environment that should receive the new bundle.
Verify `GET /api/tested-models`, Triton `/v2/health/ready`, and the expected
FIL model states before considering the rollout complete.

## Classifier guarantees

Feature order, categorical vocabularies, numeric medians, and decision
thresholds are recorded in each model's metadata. Configuration groups are
assigned as a unit so repeated measurements cannot cross train/validation/test
splits. Throughput, latency, identifiers, runtime arguments, and other
measurements are excluded from classifier inputs to avoid leakage.

`legacy_mvp.py` remains only as a migration reference. It is not part of the
production build and must not be used to publish artifacts.
